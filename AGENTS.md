# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ns8-crowdsec` is a NethServer 8 module that wraps [CrowdSec](https://docs.crowdsec.net/docs/intro) (intrusion detection/prevention). It runs the CrowdSec LAPI + agent in one container and a separate firewall-bouncer container that enforces bans via iptables/IPSET. Backend is Python 3 + bash under `imageroot/`, frontend is Vue 2 under `ui/`. Follow the `nethserver-ns8-module` skill for generic NS8 conventions (action/event structure, agent SDK, systemd pod ordering, backup patterns, ns8-ui-lib usage) — this file only covers what's specific to this repo.

## Build / test commands

- UI dev build: `cd ui && corepack enable && yarn install && yarn build` (also invoked by `build-images.sh` inside a buildah node container — do not assume a local Node toolchain is pre-provisioned).
  - If `corepack`/a Berry-compatible `yarn` aren't installed (this repo pins `yarn@4.18.0` via `package.json`'s `packageManager` field, and a bare system `yarn` binary is often the incompatible classic 1.x), fetch corepack on demand instead of giving up: `npm exec --yes corepack@latest -- yarn@4.18.0 install`, then the same `-- yarn@4.18.0 <script>` form for `build`/`lint`. No global install or root access needed.
  - On Node 17+ (this repo's webpack/loader chain predates OpenSSL 3), `yarn build`/`yarn serve` fail with `error:0308010C:digital envelope routines::unsupported` unless run with `NODE_OPTIONS=--openssl-legacy-provider` — `build-images.sh` already sets this for the buildah build; set it yourself for any local build/lint.
- UI lint/format: `cd ui && yarn lint`, `yarn format`.
- Full image build (requires `buildah`, network access, root/rootless podman storage): `./build-images.sh`. It also downloads and checksum-verifies the `crowdsec-firewall-bouncer` release tarball against `CHECKSUM` — regenerate that file (`sha256sum crowdsec-firewall-bouncer-linux-amd64.tgz > CHECKSUM`) whenever the bouncer version in `build-images.sh` changes.
- Integration tests: Robot Framework, `tests/crowdsec.robot`, run via the shared `NethServer/ns8-github-actions` test workflow (`.github/workflows/test-module.yml`) — see that repo's README for running locally. Don't try to invent a local Robot runner setup.
- No local unit-test harness exists for the Python/bash backend (`tests/` only holds the Robot suite) — stay at that convention rather than introducing a new one for backend changes.

## Architecture

### Two images, two systemd-managed containers
- `crowdsec` image: `imageroot/` + built `ui/dist` (`/ui`). Runs `<module>.service` — **rootful**, `--privileged`, `--network=host` (see `org.nethserver.rootfull=1` in `build-images.sh`). Runs the CrowdSec agent/LAPI.
- `crowdsec-firewall-bouncer` image: built separately in `build-images.sh` from a pinned GitHub release tarball of `cs-firewall-bouncer` (tracked by the custom `regexManagers` entry in `renovate.json`, not the `org.nethserver.images` label). Runs `<module>-firewall-bouncer.service`, also privileged/host-network, and actually installs the IPSET/iptables rules.
- A third unit pair, `<module>-upgrade-hub.service`/`.timer`, periodically runs `cscli hub update && cscli hub upgrade` (every ~15 days).

All three unit files are installed by `imageroot/actions/create-module` and `imageroot/update-module.d/10install_systemd_units` via `imageroot/bin/install-systemd-units`, which `envsubst`s `${MODULE_ID}` into the bouncer/timer unit templates before writing them to `/etc/systemd/system/`.

### Config is generated at container start, not only at configure-module time
Unlike the typical NS8 pattern of doing all config work inside action steps, most CrowdSec YAML config is (re)rendered from Jinja2 templates in `imageroot/templates/` by three scripts in `imageroot/bin/` — `expand-configuration`, `expand-smarthost`, `expand-bouncer-configuration` — invoked as `ExecStartPre=`/`ExecReload=` in `imageroot/crowdsec.service` / `crowdsec-firewall-bouncer.service`. `configure-module` itself just persists settings via `agent.set_env()`; the actual `crowdsec_config/*.yaml` files are only materialized on service (re)start/reload. When changing what `configure-module` accepts, check whether the corresponding `expand-*` script also needs the new env var, and whether a `systemctl reload`/`restart` is needed to see the effect.

`whitelist_ips` (an `ExecStartPost` in `crowdsec.service`) manages a `cscli allowlists` entry (`nethserver_whitelist`) for IP/CIDR whitelist entries and always adds `sos.nethesis.it`'s IP when a subscription is active; FQDN whitelist entries go through a different path — a postoverflow YAML template (`nethserver-postoverflows-whitelists.yaml`) rendered by `expand-configuration`. Keep this IP-vs-FQDN split in mind when touching whitelist logic — it's split across two files for a reason (CrowdSec's centralized allowlists only accept IP/CIDR, not domains).

### Custom "tainted" parsers/scenarios and the fake `nethesis/nethvoice` collection
`imageroot/tainted/` holds custom CrowdSec parsers/scenarios not from the CrowdSec hub: NethVoice CTI/admin-API/reports brute-force detection, Kamailio SIP brute-force detection, and a permanent Nextcloud parser. These are copied into `crowdsec_config/` by `expand-configuration`, not managed via `cscli`. The NethVoice+Kamailio set is bundled and exposed to the UI/API as a single fake collection named `nethesis/nethvoice`, toggled through the `toggle-collection` action (`imageroot/actions/toggle-collection/10toggle-collection`) which special-cases that name to flip the `NETHVOICE_COLLECTION_ENABLED` env var instead of calling `cscli collections install/remove`. Any other collection name in that action goes through real `cscli collections <install|remove>`. New "fake collection" style additions should follow this same env-var + `expand-configuration` copy pattern, not try to register with the real hub.

### Notifications
Email notifications go through `imageroot/bin/expand-smarthost`, which reads cluster smarthost settings via `agent.get_smarthost_settings()` and only renders `crowdsec_config/notifications/email.yaml` when both an SMTP smarthost is configured and `receiver_emails` is non-empty. The `smarthost-changed` event handler (`imageroot/events/smarthost-changed/10handler`) just restarts the service so `ExecStartPre` re-expands this file with the latest smarthost config.

### Backup scope
`imageroot/etc/state-include.conf` only backs up `volumes/data` (the CrowdSec data volume, alerts/decisions DB) and `state/secrets/bouncer_keys_firewall.secret`. All other config under `state/crowdsec_config/` is regenerated from templates/env vars on every start — do not add it to the backup list.

### No database service
This module has no MariaDB/PostgreSQL component — don't apply the DB dump/restore patterns from the general NS8 skill here; CrowdSec persists its own SQLite/data volume.

### Threat Shield: the Nethesis premium blocklists and the nethesis-insights exchange
One feature, one UI page, one env var. `THREAT_SHIELD_FEEDS` (a comma-separated list written only by `imageroot/actions/set-threat-shield/`) selects which blocklists are active: the five curated `bl.nethesis.it` feeds catalogued in `imageroot/threat-shield-feeds.json`, plus `nethesis-insights` — a **virtual feed** with no catalog entry, pulled from a different server on a different timer, but toggled through the same list. Everything about that virtual feed is defined in one place, `imageroot/bin/threat_shield.py` (`INSIGHTS_FEED_KEY`, `INSIGHTS_FEED_DESCR`, `INSIGHTS_SCENARIO`, `INSIGHTS_CONFIDENCE`, `INSIGHTS_DEFAULT_URL`, `SCENARIO_PREFIX`); `enabled_feeds()` filters to catalog keys so the premium importer never sees it, `all_feed_keys()` and `insights_enabled()` are what the actions use instead. Identity (`system_id`/`auth_token`) is always read fresh from the `cluster/subscription` Redis hash at render/run time via `threat_shield.identity()` — never persisted into the module environment — so a terminated/re-registered subscription starts working (or stops) on the very next reload with no reconfiguration.

**The entitlement verdict is a cache, and that is load-bearing.** `threat_shield.probe_status()` resolves `{entitled, type}` by HTTP-probing the first catalog feed (200 means both "entitled" and "this is the right `enterprise`/`community` URL segment"), caching it 6h in `threat_shield_entitlement.json`. `threat_shield.cached_probe_status()` reads that file and **never probes** — use it from anything on a service-start path. `expand-configuration` is `crowdsec.service`'s `ExecStartPre`, so a live probe there would stall the start up to 40s when `bl.nethesis.it` is unreachable. Because the push gate reads only the cache, four places must keep it warm: `import-threat-shield` probes before its own no-feeds early exit, `set-threat-shield` busts and re-probes, `events/subscription-changed/10refresh-entitlement` busts and re-probes before `20restart` reloads, and `list-threat-shield` probes on every UI page load. Adding a new caller of `cached_probe_status()` means checking that list still covers it.

Confidence ratings (`threat_shield.get_confidence()`) are a behaviour-identical port of NethSecurity's `ns.threatshield`: `-1` for any non-enterprise subscription, else `lvl1` → 10, `lvl2` → 8, `lvl3` → 6, `lvl4` → 5. Keep it that way — the point is that both products rate the same feed the same. `nethesis-insights` has no level suffix and is special-cased to `INSIGHTS_CONFIDENCE`.

- **Premium feeds (pull)**: `imageroot/bin/import-threat-shield`, on `<module>-threat-shield.timer` (6h, decisions last 7h). Flush-and-reimport per feed, tagged `scenario: threat-shield/<key>` — that per-feed tag is what keeps a failing or disabled feed from touching another feed's rows, or anything from CAPI/hub/manual bans/the insights import. Also refreshes the Nethesis global allowlist into its own `cscli allowlists` entry `nethesis_threat_shield`, applied *before* the import, and deliberately separate from `nethserver_whitelist` (which `whitelist_ips` recreates from `WHITELISTS` on every start) so the two managers cannot clobber each other. Outcome → `threat_shield_last_import.json`.
- **Insights push**: reuses CrowdSec's own `notification-http` plugin (same mechanism as email, see Notifications above). `imageroot/bin/expand-configuration` renders `imageroot/templates/nethesis-insights.yaml` into `crowdsec_config/notifications/` only when `cached_probe_status()` says entitled *and* the subscription has both identity fields; it also flips a `nethesis_insights` flag consumed by `profiles.yaml.local` to wire (or omit) the notification from the active profile. **The push has no switch and does not follow the feed selection** — it follows the entitlement alone, so clearing `THREAT_SHIELD_FEEDS` stops every import but keeps shipping this node's own ban decisions. That asymmetry is intentional; do not "fix" it by gating on the feed list.
- **Insights pull**: `imageroot/bin/import-blocklist`, run by its own `<module>-import.timer`/`.service` pair (`imageroot/crowdsec-import.{service,timer}`, installed the same `envsubst` way as the hub-upgrade timer). Gated on `insights_enabled()` *and* the cached entitlement; either gate failing flushes this feature's own rows rather than letting them age out. Each run is a flush-and-reimport, never a diff: `cscli decisions delete --origin cscli-import --scenario nethesis-insights` then `cscli decisions import ... -R nethesis-insights` — that bare scenario tag (no `threat-shield/` prefix) is load-bearing, it's what lets the delete step touch only this feature's own prior import. `cscli decisions import` (not `add`) always tags origin `cscli-import` regardless of `-R`; there is no way to set a custom origin. Outcome → `insights_last_import.json`.
- **The two status files are merged for the UI, not on disk**: `threat_shield_last_import.json` carries one run-level timestamp for every premium feed, `insights_last_import.json` is a flat single-feed record on a 15-minute cadence. `list-threat-shield/10list` merges them into one `last_import.feeds` map, stamping each entry with *its own* timestamp — the cadences differ, so a shared timestamp would be a lie. Both files are siblings of `crowdsec_config/`, not inside it, and deliberately out of the backup list: disposable status caches. `get-configuration` carries **no** insights data; `list-threat-shield` is the single source.
- **Allowlist request**: `imageroot/actions/request-allowlist/` is a thin, mostly-unvalidated forward of `{cidr, reason}` to the server's `POST /v1/allowlist-requests`, gated on the cached entitlement (contract from nethesis-insights' own OpenAPI spec, not duplicated here) — the server is the source of truth for validation, this action just relays its `{accepted, requests}` response or its rejection.

## UI structure

Views under `ui/src/views/`: `Status`, `Settings`, `Detections`, `Collections`, `Blocklists`, `ThreatShield`, `About` (routes in `ui/src/router/index.js`, nav entries in `ui/src/components/AppSideMenuContent.vue` — a new view needs both, plus an i18n namespace in `ui/public/i18n/en/translation.json`; `AppMobileSideMenu.vue` just re-renders `AppSideMenuContent`, nothing separate needed there). `Blocklists.vue` covers both the local allowlist and the CrowdSec Central API community blocklist/console-enrollment status (backed by `get-capi-status`, `get-capi-count`, `search-capi-decision`). `ThreatShield.vue` is the whole premium-intelligence panel — entitlement badge, the six blocklist toggles with their confidence dot meters, the merged "Last update" card, the decision search box and the allowlist-exception form — backed by `list-threat-shield`/`set-threat-shield`/`search-threat-shield-decision`/`request-allowlist`. Without a subscription or the entitlement it renders only its banner: every card is gated on `loading.listThreatShield || canEdit`, the `loading` half being what keeps the skeletons visible during the first load (both flags start `false`). Carbon icons bound as `:icon="…"` come from the `IconService` mixin's `data()`, so they need no local import. Standard NS8/Carbon/ns8-ui-lib conventions apply — see the `nethserver-ns8-module` skill; the load-bearing one specific to this repo is that every backend call goes through the `TaskService` mixin's `createModuleTaskForApp` + one-shot `core.$root` `-completed-`/`-aborted-`/`-validation-failed-` events keyed by a per-call `eventId` — there's no separate API/service layer or Vuex module for backend calls.

Built `ui/dist` is baked into the **`crowdsec` module image itself** at `/ui` (`build-images.sh`'s `buildah add "${container}" ui/dist /ui`, where `container` is a `scratch`-based NS8 module image, distinct from the actual `docker.io/crowdsecurity/crowdsec` application image referenced by `org.nethserver.images`). It is **not** extracted into `AGENT_INSTALL_DIR` (e.g. `/var/lib/nethserver/crowdsec1/`), which never gets a `ui/` directory — but it *is* extracted by the cluster to `/var/lib/nethserver/cluster/ui/apps/<module id>/` (owned `rocky:rocky`, alongside cluster-written `metadata.json`/`shortcuts.json`). So live-testing a UI change needs no image rebuild: `rsync ui/dist/` into that directory (excluding those two cluster-owned files, and pruning chunks of any view you deleted, since rsync without `--delete` leaves them behind). `imageroot/` changes go the analogous way, straight into `AGENT_INSTALL_DIR`.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ns8-crowdsec` is a NethServer 8 module that wraps [CrowdSec](https://docs.crowdsec.net/docs/intro) (intrusion detection/prevention). It runs the CrowdSec LAPI + agent in one container and a separate firewall-bouncer container that enforces bans via iptables/IPSET. Backend is Python 3 + bash under `imageroot/`, frontend is Vue 2 under `ui/`. Follow the `nethserver-ns8-module` skill for generic NS8 conventions (action/event structure, agent SDK, systemd pod ordering, backup patterns, ns8-ui-lib usage) — this file only covers what's specific to this repo.

## Build / test commands

- UI dev build: `cd ui && corepack enable && yarn install && yarn build` (also invoked by `build-images.sh` inside a buildah node container — do not assume a local Node toolchain is pre-provisioned).
  - No corepack/Berry yarn locally: `npm exec --yes corepack@latest -- yarn@4.18.0 <install|build|lint>`.
  - Node 17+: prefix local build/lint with `NODE_OPTIONS=--openssl-legacy-provider` (`build-images.sh` already does).
- UI lint/format: `cd ui && yarn lint`, `yarn format`.
- Full image build (requires `buildah`, network access, root/rootless podman storage): `./build-images.sh`. It also downloads and checksum-verifies the `crowdsec-firewall-bouncer` release tarball against `CHECKSUM` — regenerate that file (`sha256sum crowdsec-firewall-bouncer-linux-amd64.tgz > CHECKSUM`) whenever the bouncer version in `build-images.sh` changes.
- Integration tests: Robot Framework, `tests/NN__<area>.robot` (one suite per area, run in name order) sharing keywords from `tests/crowdsec.resource`, run via the shared `NethServer/ns8-github-actions` test workflow (`.github/workflows/test-module.yml`) — see that repo's README for running locally. Don't try to invent a local Robot runner setup.
- No unit-test harness for the Python/bash backend; don't add one.

## Architecture

### Two images, two systemd-managed containers
- `crowdsec` image: `imageroot/` + built `ui/dist` (`/ui`). Runs `<module>.service` — **rootful**, `--privileged`, `--network=host` (see `org.nethserver.rootfull=1` in `build-images.sh`). Runs the CrowdSec agent/LAPI.
- `crowdsec-firewall-bouncer` image: built separately in `build-images.sh` from a pinned GitHub release tarball of `cs-firewall-bouncer` (tracked by the custom `regexManagers` entry in `renovate.json`, not the `org.nethserver.images` label). Runs `<module>-firewall-bouncer.service`, also privileged/host-network, and actually installs the IPSET/iptables rules.
- A third unit pair, `<module>-upgrade-hub.service`/`.timer`, periodically runs `cscli hub update && cscli hub upgrade` (every ~15 days).

All three unit files are installed by `imageroot/actions/create-module` and `imageroot/update-module.d/10install_systemd_units` via `imageroot/bin/install-systemd-units`, which `envsubst`s `${MODULE_ID}` into the bouncer/timer unit templates before writing them to `/etc/systemd/system/`.

### Config is generated at container start, not only at configure-module time
Unlike the typical NS8 pattern of doing all config work inside action steps, most CrowdSec YAML config is (re)rendered from Jinja2 templates in `imageroot/templates/` by three scripts in `imageroot/bin/` — `expand-configuration`, `expand-smarthost`, `expand-bouncer-configuration` — invoked as `ExecStartPre=`/`ExecReload=` in `imageroot/crowdsec.service` / `crowdsec-firewall-bouncer.service`. `configure-module` itself just persists settings via `agent.set_env()`; the actual `crowdsec_config/*.yaml` files are only materialized on service (re)start/reload. When changing what `configure-module` accepts, check whether the corresponding `expand-*` script also needs the new env var, and whether a `systemctl reload`/`restart` is needed to see the effect.

`whitelist_ips` (an `ExecStartPost` in `crowdsec.service`) manages a `cscli allowlists` entry (`nethserver_whitelist`) for IP/CIDR whitelist entries and always adds `sos.nethesis.it`'s IP when a subscription is active; FQDN whitelist entries go through a different path — a postoverflow YAML template (`nethserver-postoverflows-whitelists.yaml`) rendered by `expand-configuration`. Keep this IP-vs-FQDN split in mind when touching whitelist logic — it's split across two files for a reason (CrowdSec's centralized allowlists only accept IP/CIDR, not domains).

### Custom "tainted" parsers/scenarios and the fake `nethesis/nethvoice` and `nethesis/webtop` collections
`imageroot/tainted/` holds custom CrowdSec parsers/scenarios not from the CrowdSec hub: NethVoice CTI/admin-API/reports brute-force detection, Kamailio SIP brute-force detection, a permanent Nextcloud parser, WebTop login brute-force detection (keyed on the `webtop-auth:` prefix from ns8-webtop's logback override, real client IP in `client=`), and an always-on Mattermost whitelist (skips ID-ending API GET/HEADs with plain path and query, which trip `http-crawl-non_statics`). These are copied into `crowdsec_config/` by `expand-configuration`, not managed via `cscli`. The NethVoice+Kamailio set is bundled and exposed to the UI/API as a single fake collection named `nethesis/nethvoice`, toggled through the `toggle-collection` action (`imageroot/actions/toggle-collection/10toggle-collection`) which special-cases that name to flip the `NETHVOICE_COLLECTION_ENABLED` env var instead of calling `cscli collections install/remove`. WebTop is a second fake collection, `nethesis/webtop`, on the same pattern with `WEBTOP_COLLECTION_ENABLED` (default on, also on update since it used to be always-on). Any other collection name in that action goes through real `cscli collections <install|remove>`. New "fake collection" style additions should follow this same env-var + `expand-configuration` copy pattern, not try to register with the real hub.

### Notifications
Email notifications go through `imageroot/bin/expand-smarthost`, which reads cluster smarthost settings via `agent.get_smarthost_settings()` and only renders `crowdsec_config/notifications/email.yaml` when both an SMTP smarthost is configured and `receiver_emails` is non-empty. The `smarthost-changed` event handler (`imageroot/events/smarthost-changed/10handler`) just restarts the service so `ExecStartPre` re-expands this file with the latest smarthost config.

### Backup scope
`imageroot/etc/state-include.conf` only backs up `volumes/data` (the CrowdSec data volume, alerts/decisions DB), `state/secrets/bouncer_keys_firewall.secret` and `state/threat_shield_lists.json` (restic skips it when missing). All other config under `state/crowdsec_config/` is regenerated from templates/env vars on every start — do not add it to the backup list.

### No database service
This module has no MariaDB/PostgreSQL component — don't apply the DB dump/restore patterns from the general NS8 skill here; CrowdSec persists its own SQLite/data volume.

### Threat Shield (Nethesis blocklists + Insights)
- `THREAT_SHIELD_FEEDS` (written only by `set-threat-shield`) picks feeds from `imageroot/etc/threat-shield-feeds.json`: five `bl.nethesis.it` feeds (NethSecurity's catalog, but under `/plain/__TYPE__/crowdsec-nethesis-blocklist/`: bl.nethesis.it checks the `crowdsec-advanced-threat-shield` entitlement there, not NethSecurity's `ng-blacklist`) plus `nethesis-insights`. Insights' `url_4` has no `__TYPE__` and is the only place its host is set (`threat_shield.insights_url()`); `premium_feeds()` skips it where a `bl.nethesis.it` feed is needed.
- Identity (`system_id`/`auth_token`) is read fresh from Redis `cluster/subscription` via `threat_shield.identity()`, never stored in the module env.
- Subscription alone enables the Insights push and the Nethesis allowlist; the entitlement only gates blocklist downloads. Keep that split. The Nethesis allowlist is always on with a subscription: no toggle.
- Custom lists: rows in `threat_shield_lists.json` (state, backed up; not env vars: systemd `EnvironmentFile` mangles JSON quoting), written by `set-threat-shield`, read via `load_lists()`, which drops rows failing `valid_row()` and raises `ValueError` on a broken file: then the import touches no custom allowlist nor custom feed. Names end up in cscli allowlist names and nft set/counter names, so they are re-validated in Python. Custom allowlist → cscli allowlist `threat_shield_<name>` (stale ones swept by prefix); custom blocklist → feed key `custom-<name>`, selected in `THREAT_SHIELD_FEEDS`, confidence -1. They need no identity nor entitlement. A custom URL may hold `user:pass@`, which `fetch()` sends as HTTP Basic (never after a redirect); never send the subscription credentials to a custom URL. `list-threat-shield` returns the URL with its credentials, the edit form needs it. Custom blocklist entries failing `bannable()` (loopback, link-local, multicast, reserved, and private unless `BAN_LOCAL_NETWORK=True`) are skipped at import. At most `MAX_ENTRIES` (100000) values per custom list or allowlist.
- Entitlement is cached 6h in `threat_shield_entitlement.json` by `probe_status()`. Only clear answers (200, 4xx but 408/429) are cached: a network blip must never read as "not entitled". On service-start paths (`expand-configuration`) and in `request-allowlist` use `cached_probe_status()`, which never probes. Kept warm by `import-threat-shield`, `set-threat-shield`, `subscription-changed/10refresh-entitlement` and `list-threat-shield` (while the verdict is "no").
- Confidence (`get_confidence()`) mirrors NethSecurity's `ns.threatshield`: -1 if not enterprise, lvl1→10, lvl2→8, lvl3→6, lvl4→5; Insights → `INSIGHTS_CONFIDENCE`.
- Import: `bin/import-threat-shield` on `<module>-threat-shield.timer` (30 min, decisions last 65m), enabled only with an identity or a custom list (`bin/sync-threat-shield-timer`, also run by `set-threat-shield` and `restore-module`). Allowlists first; if the Nethesis one is wanted but was never fetched (or is empty), import no blocklist. A custom allowlist that never loaded only reports its error on its row. Per feed: import the new list, then hard-delete the old alerts (`cscli alerts delete --id`), as `decisions delete` leaves rows that inflate `GetDecisionsCount()`. Then `refresh_firewall()` rewrites the bouncer's `*-blacklists-cscli-import` nft sets from the DB in one transaction (flush + add, 65m), because the bouncer adds an address once and never renews its timeout. Rows are told apart only by `scenario: threat-shield/<key>` (origin is always `cscli-import`). Feed CIDRs wider than one address are dropped (mostly `nethesislvl3`): the nftables bouncer strips the prefix and would block only the first address. The allowlist keeps its CIDRs.
- Blocked counts: count-only nft table `inet threat_shield` (priority -20, before the bouncer's -10), one counter + v4/v6 sets per enabled feed, rules by confidence with `return` so a packet is credited once. Rebuilt by `refresh_counting()` from the banned addresses (allowlisted ones excluded); each run first reads+zeroes the counters into `threat_shield_blocked.json` (24h of slots, not backed up). `list-threat-shield` adds the live counters (`blocked_24h`). `destroy-module` drops the table.
- Allowlists: their own `cscli allowlists` entries (`nethesis_threat_shield`, `threat_shield_<name>`), separate from `nethserver_whitelist`; updated add-before-remove, an empty download is a failure.
- Status in `threat_shield_last_import.json` (not backed up); `list-threat-shield` is the only UI source, `get-configuration` has no Threat Shield data. Its `allowlists` rows are configuration only (the built-in `nethesis` row is always listed, read-only, `enabled` only with a subscription); each row's import outcome is in `last_import.allowlists[name]`.
- Push: `templates/nethesis-insights.yaml` via `notification-http`, rendered by `expand-configuration` whenever there is an identity, unless `NETHESIS_INSIGHTS_PUSH=False` (CLI-only opt-out, default on). Deliberately not gated on the feed selection or the entitlement.
- `request-allowlist`: thin relay to Insights `POST /blocklist/crowdsec/v1/allowlist-requests`, gated on the cached entitlement. CLI only, no UI.

### Permanent bans (local blocklist)
- `LOCAL_BLOCKLIST` (env, comma-separated single addresses) is the source of truth, written by `set-local-blocklist`, returned by `get-configuration` as `local_blocklist`. `bin/sync-local-blocklist` makes the bans match it; it runs from `set-local-blocklist`, as `ExecStartPost` and after `delete-detections` (whose flush drops them). A permanent ban added or removed outside the list is undone by the next sync, so there is no add-ban action and `unban-ip` never touches permanent bans.
- A permanent ban is `cscli decisions add -d 876000h -R "permanent: local blocklist"` (origin `cscli`: never `decisions import`, whose `cscli-import` nft set `refresh_firewall()` rewrites with Threat Shield rows only). The `permanent:` scenario prefix is the only marker, matched in the sync, `unban-ip` (unban and unban_all skip them), `list-banned-ip` and `list-detections`. Only single addresses (the bouncer strips prefixes).
- The bouncer skips an address already in its sets, and the LAPI stream hides a deletion behind any longer decision of the same value: the sync deletes every ban of the new addresses (`--contained`, Threat Shield too), waits once until the bouncer drops them from nft, then adds the long bans. `cscli decisions list` shows an address once (newest alert), so the sync and `list-banned-ip` read `alerts list --origin cscli` instead.

## UI structure

Views under `ui/src/views/`: `Status`, `Activity`, `Collections`, `ThreatShield`, `Settings`, `About`. A new view needs a route (`ui/src/router/index.js`), a nav entry (`ui/src/components/AppSideMenuContent.vue`) and an i18n namespace. Tab pages keep the tab in `q.view` and draw `NsTabs` only after the URL binding (`urlBound`), or the first tab wins. `Activity.vue` (was Detections, `/detections` redirects): detections with an Action filter (All, No action, Banned, Ban expired), Unban per banned row, Unban all, Unban in the details window. `ThreatShield.vue` ("Threat Shield IP"): Blocklist/Allowlist feeds (in the view: `list-/set-threat-shield`, `search-threat-shield-decision`, catalog feeds gated on `canEdit` = subscription + entitlement), Local blocklist (`LocalBlocklist.vue`, text box: `set-local-blocklist`), Local allowlist (`LocalAllowlist.vue`) and CrowdSec community blocklist (`CommunityBlocklist.vue`: `get-capi-status`, `get-capi-count`, `search-capi-decision`). The last two share the view's `get-configuration` output (`config` prop, `config-changed` event): `configure-module` takes the whole config. `/blocklists` redirects there. Shared helpers live in `ui/src/lib/`. Standard NS8/Carbon/ns8-ui-lib conventions apply — see the `nethserver-ns8-module` skill; backend calls go only through `TaskService`'s `createModuleTaskForApp` + one-shot `core.$root` events keyed by `eventId`.

Live test without rebuilding the image: the UI is served from `/var/lib/nethserver/cluster/ui/apps/<module id>/`, so `rsync -a --delete --chown=rocky:rocky --exclude metadata.json --exclude shortcuts.json ui/dist/` there; `imageroot/` changes go straight into `AGENT_INSTALL_DIR`.
